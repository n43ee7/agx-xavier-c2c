## 3. Issues found and fixed today

1. **Remote memory capped at about 165 MB/s.** c2c-memd and c2c-rmem set
   `SO_SNDBUF`/`SO_RCVBUF` to 8 MiB. That disables TCP autotuning, and the
   kernel clamps the value to wmem_max (about 416 KiB); 416 KiB divided by the
   loaded RTT ≈ 165 MB/s. Fix: let TCP autotune. Raw went from 163/166 to
   400/412 MB/s.
2. **Swap page-in slow (0.046 GiB/s).** `vm.page-cluster=3` (32 KiB readahead)
   is tuned for local disks. The tests set 5 (128 KiB) while remote memory is
   attached → 0.081 GiB/s. A value of 7 gave no further gain.
3. **Report showed 2.0 GiB in slave RAM instead of 8.5.** mawk's `%d` clamps
   at 2^31. Fixed with `%.0f`.
4. **KERNEL PANIC on the master during a full suite (T05, 20:36).**
   ```
   Unable to handle kernel NULL pointer dereference at 0000000000000000
   CPU: 6 PID: 2 Comm: kthreadd
   pc : kthread_should_stop+0x28/0x50
     sk_stream_wait_memory / tcp_sendmsg_locked / nbd send / blk_mq / swap_writepage /
     pageout / shrink_page_list / try_to_free_pages / __vmalloc_node_range /
     copy_process / kernel_thread / kthreadd
   Code: ... ldr x0,[x0,#0x640] ; ... (f9400000 = ldr x0,[x0])   <- NULL
   ```
   This is a bug in the L4T 5.10 kernel. `kthreadd` (PID 2) has no
   `struct kthread`: `task->set_child_tid`, at offset 0x640, is NULL.
   While forking, `kthreadd` did direct reclaim and swapped a page out to
   nbd; the TCP send buffer was full, and the wait for space called
   `kthread_should_stop()` → NULL dereference → panic → reboot. The board
   came back cleanly, with the link UP and no leftover swap or sysctls.
   Before the fix it happened in 1 of 6 T05 runs.
   - **Fix: `kernel/kfix/c2c_kfix.ko`.** It backports the upstream (5.17+)
     approach at runtime by giving `kthreadd` a zeroed `struct kthread`.
     - At load it checks that PID 2 is `kthreadd` and that the pointer is
       NULL, then self-tests through `kthread_func()`, which uses the same
       lookup as the crash.
     - The kernel log confirms it:
       `c2c_kfix: kthreadd now has a struct kthread (set_child_tid @ +0x640)`.
       The offset equals the one the faulting instruction used.
     - It loads at boot through `modules-load.d`, and is rebuilt after
       kernel updates by `c2c-ensure-module.sh`.
     - `c2c-rmem` refuses to enable swap unless it is loaded (`-f` overrides).
   - **Defense in depth** (kept):
     - 64 MiB forced socket send buffer (`SO_SNDBUFFORCE`) and
       `max_sectors_kb=128`, so nbd's maximum in-flight data
       (2 × 128 × 128 KiB) always fits and a send never waits;
     - `vm.watermark_scale_factor=200` while remote memory is attached, so
       kswapd does the swapping, not random tasks;
     - c2cd is mlocked, `PR_SET_IO_FLUSHER` and OOM-exempt.
   - **Validation after the fix:**
     - 3 consecutive T05 runs (mitigations only);
     - then with c2c_kfix: the full T01–T07 suite plus 2 more T05 runs;
     - 6 runs of 20.5 GiB on the 14.5 GiB master in all, all PASS, no reboot.
5. **Alarming `I/O error, dev nbd0, sector 0` lines in dmesg at every
   detach.** They come from a partition-table rescan of a device that was
   just disconnected. Fix: c2c-rmem loads nbd with `max_part=0`. Since then,
   4 of 5 detaches logged nothing. One logged a single udev probe read of the
   device's last sector during the disconnect. That one is cosmetic and harmless.
6. **SSH from the test harness.** Installing a persistent SSH key on the slave
   was blocked, so the harness uses the slave password from an environment
   variable (`C2C_PEER_PASS`, never written to disk) and one multiplexed
   ssh connection over c2c0. An optional key mode is available:
   `setup_tests.sh --with-key`.

## 4. Known limits (honest list)

- Remote RAM through the swap path adds **capacity, not speed**: page-in is
  about 0.09–0.12 GiB/s, against 30+ GiB/s for local RAM. Bulk data, such as
  model weights or tensors, needs a dedicated zero-copy channel. That is the
  next step.
- If the link is down for longer than the 60 s nbd timeout, or the slave
  reboots while pages are swapped out, the processes that own those pages
  get I/O errors (SIGBUS). Short outages are fine (T07).
- The GPU and CPU pools dispatch unmodified programs **to** the slave. A
  program running on the master does not yet see the slave's GPU as a local
  CUDA device; that would need CUDA API forwarding.
- In T06, c2cd's master-side `gpu_util` read 0.8% while its GPU was busy;
  the slave side read 99.7% correctly. This is a telemetry sampling quirk on
  the local node and needs a look.
- T03 scales 1.69×, not 2×: the master also runs the 8 ssh streams and c2cd
  while compressing.
