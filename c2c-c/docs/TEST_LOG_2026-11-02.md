### 2.4 Problems found and solved while building it

1. **The CUDA runtime only uses `cuGetProcAddress`.** cudart 11.4 looks up
   nearly every driver function through it. The library hands out its own
   entry point for each of NVIDIA's 533 driver functions: 127 implemented,
   406 generated trampolines that route by the calling thread's context.
2. **Undocumented driver tables.** cudart also calls six private "export
   tables". By tracing them (logging trampolines) I found that table
   `6bd5fb6c…`:
   - slot 2 returns the primary context for a device ordinal;
   - slot 6 loads a registered fatbinary into the current context.

   Both are intercepted. Everything else in those tables works unchanged,
   because each remote context is backed by a real shadow context on the
   identical local GPU.
3. **Identical device addresses on both GPUs.** Both drivers hand out
   `0x203…` pointers, so pointers would collide. Fix: master and slave
   reserve one shared window of GPU virtual address space with CUDA's VMM
   API (`0x991000000`, 35 GiB). The side whose VMM area starts lower pads up
   to the other's start. The slave maps each allocation at the exact address
   the master chose.
   - Found on the way: the driver refuses hinted reservations outside its
     current VMM bump region.
   - Found on the way: once a process has two contexts on a GPU, large
     reservations fail (error 208). The window is therefore reserved before
     the shadow context is created.
4. **GPU power gating cost about 250 µs per synchronous call.** On the
   slave, launch + sync took 17 µs when busy, but 110–350 µs after an idle
   gap of 50 µs or more. With `elpg_enable=0` it stayed at 13–19 µs at any
   gap. c2c-gpud turns ELPG off while a client is connected and restores it
   5 s after the last one leaves. Result: launch + sync went from 640 µs to
   352 µs.
5. **Server-side syscalls capped launches at 29.5k/s.** A buffered reader
   (one `recv` for many messages) raised this to 167k/s; client-side
   batching brought it to 257k/s.
6. **Textures, arrays and cooperative launch.** Added remote CUDA arrays,
   one general 2D/3D copy (pitched copies became one message instead of one
   per row), texture and surface objects, and cooperative launch.

## 3. Remote RAM: page-in about 75% faster

On 5.10 the per-VMA swap readahead is capped at 2⁵ pages (128 KiB) whatever
`vm.page-cluster` says. The older cluster readahead (`vma_ra_enabled=false`)
honours `page-cluster` fully. T04 sweep (8 GiB under a 2 GiB cap):

| page-cluster | per-VMA readahead | page-out GiB/s | page-in GiB/s |
|---|---|---|---|
| 5 | on (old default) | 0.175 | 0.083 |
| 5 | off | 0.176 | 0.082 |
| 6 | off | 0.177 | 0.117 |
| **7** | **off** | 0.177 | **0.141** |
| 8 | off | 0.176 | 0.140 |

T05 (20.5 GiB on the 14.5 GiB master):

| configuration | write GiB/s | verify GiB/s |
|---|---|---|
| page-cluster 5, per-VMA readahead on | 0.423 | 0.086 |
| page-cluster 7, per-VMA readahead on | 0.414 | 0.090 |
| **page-cluster 7, per-VMA readahead off (new default)** | 0.412 / 0.353 | **0.149 / 0.149** |

`c2c-rmem attach -w` now applies these settings itself, together with
`min_free_kbytes` ≥ 256 MiB and `watermark_scale_factor` ≥ 200. It saves the
previous values in `/run/c2c/rmem-vm.saved` and restores them at detach.
Options: `-r N` sets the order, `-V` keeps per-VMA readahead, `-T` skips
tuning. The tests no longer touch sysctls themselves.

## 4. Telemetry: master GPU load

c2cd sampled the GPU load counter once every 2 s. That counter is a short
moving window, so bursty CUDA work read as 0% most of the time; the slave
showed the same effect, jumping between 0 and 99.7%. A 20 ms sampler thread
now averages the counter over each telemetry period. The wire format is
unchanged. T06 master GPU peak: 0.8% before, 46.6% now (the window average
of a bursty benchmark).

## 5. Link latency

| layer | round trip |
|---|---|
| raw USB, in-kernel ping-pong (`test_bw_spd`, 8 B) | 90–120 µs |
| c2cd control-channel ping | 274–296 µs min |
| TCP request/response over c2c0 (16 B) | 369 µs → **336 µs** with c2cd busy-polling |
| remote GPU synchronize | 352 µs |

New in c2cd: `busy_poll_us=200` (config key). For 200 µs after any traffic
the rx and tun loops poll without sleeping, so a reply is picked up without
a thread wake-up. CPU clocks were already pinned at 2.27 GHz with idle
states off, and USB3 U1/U2 are disabled. The rest is two TCP/TUN passes and
c2cd per side. Going lower would need a dedicated non-TCP channel for GPU
calls.

## 6. Known limits (unchanged on purpose, or not fixable here)

- **Link speed and latency.** Data movement to and from the remote GPU is
  capped by the link: ~465 MB/s and ~0.35 ms per synchronous call. Keep data
  resident on the remote GPU.
- **Not supported on the remote GPU** (it reports the matching capability
  as 0): unified/managed memory, zero-copy mapped host memory, CUDA graphs
  and stream capture, memory pools and `cudaMallocAsync`, IPC, multi-device
  cooperative launch, mipmapped arrays, legacy texture references.
  Device-side `printf` prints on the slave.
- **Remote RAM.** Page-in is still latency-bound (one round trip per fault
  cluster). Outages longer than the 60 s nbd timeout fail I/O to remote
  pages.
